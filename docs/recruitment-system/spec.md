# Spec: 招聘系统 HR 后台（首版）前端页面

## 1. Context

- 需求来源: 用户在「需求澄清」节点确认，为"招聘系统前端页面"的首版设计。
- 当前产品现状: 工作区仓库 `repos/fanym22/Delivery-AI-Test` 目前是一个 Python 记账 CLI 项目，尚未存在招聘系统前端代码，无既有路由、组件或设计系统可供复用；`knowledge/design-system/` 为空，原型将使用企业级 SaaS 通用视觉基线（专业商务蓝主题）作为起点，待后续接入真实设计系统时替换 token。
- 目标用户: 企业内部 HR/招聘者（Recruiter），辅助其完成职位发布、候选人筛选与面试推进的日常工作。
- 核心业务场景:
  1. 职位管理: 查看所有在招/已关闭职位，新建或编辑职位，控制职位上下架。
  2. 候选人库与简历筛选: 在候选人池/职位维度下浏览候选人，按关键字、阶段、标签、时间等维度筛选，快速判断匹配度。
  3. 面试流水线与进度看板: 以 Kanban 看板按面试阶段呈现候选人，支持拖拽流转、查看详情与推进状态。

## 2. Goals and Non-Goals

### Goals

- G1: 在桌面端提供 HR 首版招聘工作闭环所需的 5 个核心页面，覆盖登录 → 职位管理 → 候选人筛选 → 面试推进 → 候选人详情查看的主路径。
- G2: 通过可点击 HTML 原型，将信息架构、核心交互和视觉风格具象化，作为下游 AI-编码节点的实现依据。
- G3: 对关键异常/空状态（无数据、加载中、表单校验失败、权限不足）给出明确交互与文案，避免下游实现时产生歧义。
- G4: 视觉风格符合"专业商务蓝"主题，信息密度适合 PC 端长时间办公场景，主色、字体、间距、组件状态在 5 个页面中保持一致。

### Non-Goals

- NG1: 不覆盖候选人投递门户（C 端）、面试官端、Offer 审批、薪酬管理、报表分析、消息通知、系统设置等模块，列入后续迭代。
- NG2: 不实现真实后端对接、登录鉴权、简历解析、文件上传、邮件/日历集成，原型以 mock 数据和交互模拟呈现。
- NG3: 不做移动端 APP 与响应式适配，仅保证在常见桌面分辨率（1280×800 及以上）下正常显示。
- NG4: 不输出真实接口字段与数据库模型，对数据契约的描述仅服务于页面展示与交互，后续由 AI-编码/技术设计节点细化。

## 3. Glossary

| 术语 | 含义 |

| Candidate / 候选人 | 投递或被推荐进入招聘流程的人员，包含基本信息、简历、标签、当前阶段、投递职位等。 |

## 4. Functional Requirements

### REQ-001: 登录页

- User Story: 作为 HR，我希望通过账号密码登录招聘后台，以便安全访问内部招聘数据。
- Priority: P0
- Description: 提供登录入口，验证账号与密码格式，登录成功后进入职位列表页；失败时给出明确错误提示。

Acceptance Requirements (EARS):
- REQ-001.1: 当用户未登录访问任意后台页面时，系统应重定向到登录页。
- REQ-001.2: 当用户输入的账号或密码为空时，登录按钮应处于禁用状态，并在失焦时提示必填校验信息。
- REQ-001.3: 当用户点击"登录"且账号密码格式正确时，系统应显示加载状态并在成功后跳转至职位列表页。
- REQ-001.4: 当登录接口返回账号或密码错误时，系统应在表单顶部展示错误提示"账号或密码错误，请重试"，不清除用户已输入的账号。
- REQ-001.5: 原型阶段登录使用前端 mock，任意格式合法的账号密码均可"登录成功"。

Gherkin:
```gherkin
Scenario: 登录成功进入职位列表
  Given 用户处于登录页
  When 用户输入合法账号与密码并点击"登录"
  Then 登录按钮进入加载状态
  And 登录成功后跳转至"职位管理"列表页

Scenario: 账号密码错误
  Given 用户处于登录页
  When 用户输入账号与密码并点击"登录"
  And 后端返回"账号或密码错误"
  Then 表单顶部展示错误提示
  And 账号输入框保留已输入内容，密码框清空并聚焦
```

### REQ-002: 职位列表页

- User Story: 作为 HR，我希望集中查看和管理所有职位，以便快速定位需要跟进的岗位。
- Priority: P0
- Description: 列表展示职位卡片/行，支持关键字搜索、按部门/状态/地点筛选，支持发布、暂停、关闭、新建、编辑、进入候选人看板等操作。

Acceptance Requirements (EARS):
- REQ-002.1: 页面顶部应包含页面标题"职位管理"、"新建职位"主按钮以及搜索/筛选区（关键字、部门、状态、地点）。
- REQ-002.2: 列表应按"最后更新时间"倒序展示职位，每条展示字段包括: 职位名称、部门、工作地点、招聘人数、负责人、状态、最后更新时间、候选人进度摘要（总数/在面/已发 Offer）。
- REQ-002.3: 当职位数为 0（或筛选后无结果）时，系统应展示空状态插画 + "还没有职位，点击右上角新建职位开始招聘吧"提示，并保留"新建职位"按钮入口。
- REQ-002.4: 当用户点击某一行职位时，系统应跳转到对应职位的"候选人看板"页；当点击职位名称旁的"编辑"图标时，跳转到该职位的编辑页。
- REQ-002.5: 当用户点击行内"上架/暂停/关闭"操作时，系统应弹出二次确认浮层，确认后更新该职位状态并局部刷新列表，给出成功 Toast。
- REQ-002.6: 职位状态 Tag 应使用不同颜色区分: 招聘中=蓝底白字、草稿=灰底黑字、已暂停=橙底白字、已关闭=深灰底白字。

Gherkin:
```gherkin
Scenario: 筛选职位并进入看板
  Given HR 已登录并位于职位列表页
  When 在搜索框输入"前端"，并选择部门="技术"
  Then 列表仅展示匹配"前端"且部门为"技术"的职位
  When 点击某条"高级前端工程师"职位行
  Then 跳转至该职位的候选人看板页
```

### REQ-003: 职位新建/编辑页

- User Story: 作为 HR，我希望新建或修改职位信息，以便对外发布招聘需求。
- Priority: P0
- Description: 提供表单录入职位名称、所属部门、工作地点、招聘人数、经验要求、学历要求、薪资范围、职位类型（校招/社招/实习）、招聘负责人、JD 描述、发布渠道等信息；支持保存草稿与直接发布。

Acceptance Requirements (EARS):
- REQ-003.1: 新建模式下页面标题为"新建职位"，提交成功后职位状态为"招聘中"（点击"发布"）或"草稿"（点击"保存草稿"）。
- REQ-003.2: 编辑模式下页面标题为"编辑职位 · {职位名称}"，表单默认回填现有数据，进入页面时在顶部提示"上次编辑于 {time}，由 {editor} 保存"。
- REQ-003.3: 必填字段（职位名称、部门、工作地点、招聘人数、经验要求、招聘负责人、JD 描述）未填写时，点击"发布"或"保存草稿"应在对应字段下方展示红色错误提示，并滚动到首个错误字段。
- REQ-003.4: 招聘人数必须为 ≥1 的正整数；薪资范围如填写，最小值不得大于最大值；违反时就地提示。
- REQ-003.5: 用户离开页面前若存在未保存的修改，系统应弹出"你有未保存的内容，确定离开吗？"确认框。
- REQ-003.6: 提交成功后，系统应展示成功 Toast，并在 1.5s 后跳转回职位列表页；列表中新增/更新的职位应在 3s 内可见（原型中通过本地 mock 即时生效）。

Gherkin:
```gherkin
Scenario: 新建职位并发布
  Given HR 在职位列表页点击"新建职位"
  When 填写所有必填字段并点击"发布"
  Then 系统展示"职位发布成功"Toast
  And 跳转回职位列表页
  And 新职位出现在列表顶部，状态为"招聘中"

Scenario: 表单必填校验
  Given HR 在新建职位页未填写"职位名称"与"JD 描述"
  When 点击"发布"
  Then 页面滚动至首个错误字段
  And 对应字段下方展示红色错误文案
```

### REQ-004: 候选人看板页（Kanban 流水线）

- User Story: 作为 HR，我希望在一个看板上看到某职位下所有候选人的阶段分布，以便快速推进面试流程。
- Priority: P0
- Description: 以 Kanban 形式按面试阶段列展示候选人卡片；顶部展示职位基本信息与候选人整体漏斗统计；支持筛选、拖拽流转、查看详情、淘汰等操作。

Acceptance Requirements (EARS):
- REQ-004.1: 看板列应按以下顺序排列: 简历筛选、初筛、一面、二面、HR 面、Offer、已入职；已淘汰候选人不出现在列中，可通过"查看已淘汰"筛选器切换展示。
- REQ-004.2: 每张候选人卡片至少展示: 姓名、最近岗位/学历、工作年限、标签（如"985"/"大厂背景"/"急招"）、当前阶段停留时长、最近更新时间。
- REQ-004.3: 当用户拖拽卡片到另一列时，系统应弹出"确认将 {候选人} 移动至 {目标阶段}？"确认框（含可选备注输入），确认后卡片落到目标列末尾，并更新顶部漏斗数据。
- REQ-004.4: 看板顶部应支持按关键字（姓名/学校/公司）、标签、招聘负责人、更新时间范围进行筛选；筛选结果仅影响卡片集合，不改变列结构。
- REQ-004.5: 当某一列为空时，该列应展示"暂无候选人"占位文案；当职位下无任何候选人时，整个看板区域展示空状态并提供"上传简历 / 添加候选人"引导按钮（原型中为占位按钮）。
- REQ-004.6: 点击候选人卡片应在右侧抽屉中打开该候选人的详情预览，抽屉不离开当前看板上下文；点击"查看完整详情"进入候选人详情页。

Gherkin:
```gherkin
Scenario: 在看板上推进候选人阶段
  Given HR 进入某职位的候选人看板
  When 将"张三"卡片从"简历筛选"列拖拽到"初筛"列
  Then 弹出确认浮层
  When 在浮层中点击"确认"
  Then 卡片移至"初筛"列末尾
  And 顶部漏斗统计中"简历筛选"数量 -1，"初筛"数量 +1
```

### REQ-005: 候选人详情页

- User Story: 作为 HR，我希望查看单个候选人的完整信息与招聘轨迹，以便做出是否推进的判断。
- Priority: P0
- Description: 展示候选人基本信息、简历概要、技能标签、投递记录、面试历史与评价、操作时间线，并提供推进阶段、淘汰、添加评价、安排面试等操作入口。

Acceptance Requirements (EARS):
- REQ-005.1: 页面顶部展示候选人姓名、意向职位、当前阶段 Tag、联系方式（手机/邮箱，原型中可部分打码）、来源渠道。
- REQ-005.2: 页面主体采用左右两栏布局: 左侧展示简历概要（基本信息、教育经历、工作经历、项目经历、技能标签）；右侧展示招聘进度时间线（阶段变更、面试评价、备注）以及操作区（推进阶段、淘汰、添加备注、安排面试）。
- REQ-005.3: "推进阶段"按钮应打开阶段选择下拉/弹窗，仅允许向"相邻下一阶段"或"回退一步"切换（不允许跨阶段跳转，除非在备注中明确说明，原型中不强制）。
- REQ-005.4: "淘汰"按钮应弹出二次确认，要求选择淘汰原因（文化不匹配 / 技能不匹配 / 薪资预期不符 / 主动放弃 / 其他），可选填写备注，确认后候选人状态变为"已淘汰"，从看板默认列中移除。
- REQ-005.5: 添加备注后，备注应出现在右侧时间线顶部，记录操作人、时间与内容。
- REQ-005.6: 返回按钮应回到用户进入前的页面（优先回到对应职位的候选人看板）。

Gherkin:
```gherkin
Scenario: 在详情页淘汰候选人
  Given HR 在候选人详情页
  When 点击"淘汰"按钮并选择"技能不匹配"，填写备注后确认
  Then 候选人状态变为"已淘汰"
  And 时间线顶部新增一条"已淘汰：技能不匹配"记录
  And 返回看板后该候选人不再出现在默认列中
```

## 5. UX Design

### 5.1 体验目标与设计原则

- 高效优先: 信息密度适合 PC 办公场景，常用操作（筛选、查看详情、推进阶段）1–2 次点击可达。
- 专业稳重: 采用专业商务蓝主色（主色 `#1F5FEB`，辅助色 `#0F3B99`/`#E8EFFE`），中性色阶用于文本与背景；避免过度装饰。
- 状态可见: 加载、空、错误、成功、禁用状态均有明确视觉反馈；关键操作有二次确认。
- 一致性: 5 个页面共用一套顶栏、侧栏、按钮、表单、表格、Tag、抽屉、Toast 组件样式。

### 5.2 全局框架

- 顶部导航栏（高 56px，白底+1px 下分割线）: 左侧为产品 Logo"RecruitHub · 招聘管理后台"；中部为一级导航（职位管理、候选人库、报表、设置——首版仅职位管理为激活状态，其余为占位）；右侧为全局搜索、消息铃铛（占位，带小红点）、用户头像与下拉菜单（个人资料、退出登录）。
- 左侧二级菜单: 在登录页不显示；进入后台后展示 200px 宽侧栏，包含"职位列表""新建职位""候选人看板"（首版聚焦 3 项）。当前页菜单项高亮（左侧 3px 主色条 + 浅蓝底）。
- 内容区: 最小宽度 1280px，背景 `#F5F7FB`，卡片白底圆角 8px，阴影 `0 1px 2px rgba(15,23,42,0.06)`。
- 字体: 中文系统默认栈（PingFang SC / Microsoft YaHei / Segoe UI），正文 14px / 行高 22px；标题 16–20px。

### 5.3 页面清单与布局

| 页面 | 路由（原型内 hash） | 主要模块 |
|---|---|---|
| P1 登录页 | `#/login` | 左侧品牌区（Logo + 标语"高效招聘，从这里开始" + 背景插画）、右侧登录卡片（账号/密码输入、登录按钮、忘记密码链接） |
| P2 职位列表 | `#/jobs` | 顶部标题+新建按钮+筛选栏；职位列表表格；分页器（原型 mock 20 条内不分页） |
| P3 职位新建/编辑 | `#/jobs/new`、`#/jobs/:id/edit` | 分两列的表单（基础信息、职位描述），底部吸底操作栏（取消、保存草稿、发布） |
| P4 候选人看板 | `#/jobs/:id/board` | 顶部职位摘要卡 + 漏斗统计 + 筛选栏；Kanban 多列滚动区；右侧候选人预览抽屉 |
| P5 候选人详情 | `#/candidates/:id` | 顶部候选人摘要栏；左栏简历信息；右栏时间线 + 操作区；返回按钮 |

### 5.4 核心体验路径

Happy Path（登录→发布职位→推进候选人）:
1. 用户在登录页输入账号密码 → 进入职位列表。
2. 点击"新建职位"→ 填写表单 → 发布成功回到列表 → 新职位显示在顶部。
3. 点击新职位进入候选人看板 → 查看 Kanban 列分布 → 拖拽候选人到下一阶段。
4. 点击某候选人卡片 → 右侧抽屉预览 → 点击"查看完整详情"进入详情页 → 添加备注/推进阶段/淘汰。

### 5.5 分支路径与异常状态

- 未登录: 访问任意后台路由 → 重定向至 `#/login`，登录成功后跳回原目标页。
- 加载中: 列表/看板数据加载使用骨架屏（卡片/行占位），避免白屏；原型以 300ms setTimeout 模拟。
- 空状态:
  - 职位列表无数据: 插画 + "还没有职位，开始创建你的第一个职位吧" + 新建按钮。
  - 看板某列为空: 列内"暂无处于{阶段}的候选人"文案。
  - 看板全空: "该职位暂无候选人，上传简历或从候选人库添加吧" + 占位按钮。
- 表单校验: 错误字段红色边框 + 行内错误文案；提交按钮在首个错误出现时抖动一次（可选）。
- 操作反馈: 成功使用主色 Toast（顶部居中，2.5s 自动消失）；失败使用红色 Toast 并附重试按钮；危险操作（关闭职位、淘汰候选人）使用红色按钮 + 二次确认弹窗。
- 权限不足: 首版原型以单角色（HR）为主，未实现真实权限；在导航中将非首版模块（报表、设置）置灰并 Tooltip 提示"首版暂未开放"。

### 5.6 交互与组件规范

- 按钮: 主按钮蓝底白字（`#1F5FEB`），次按钮白底蓝字+1px 主色描边，危险按钮红底白字；hover 亮度上浮 6%，disabled 状态 `#C7D2E5`。
- 表格行: hover 背景 `#F0F5FF`；点击行进入职位看板，点击行内"编辑"图标进入编辑页（阻止冒泡）。
- Kanban 列: 每列最小宽度 260px，列头显示阶段名 + 人数角标；卡片可拖拽，拖拽时原卡片半透明，目标列出现蓝色虚线占位。
- 抽屉: 右侧 480px 宽滑出，背景遮罩透明度 0.45，ESC 键/点击遮罩可关闭。
- 弹窗: 宽度 420px，危险操作按钮为红色，取消按钮在左。

### 5.7 视觉与响应式约束

- 主色 `#1F5FEB`，辅助色：成功 `#16A34A`、警告 `#F59E0B`、错误 `#DC2626`、信息 `#0EA5E9`；文本主色 `#0F172A`、次色 `#475569`、弱色 `#94A3B8`。
- 间距基准 4px 网格（4/8/12/16/24/32）。
- 仅针对桌面端（≥1280px 宽度）做布局优化，<1280px 时内容区出现横向滚动条，不做移动端断点适配。
- 所有可交互元素需具备可见 focus 轮廓（2px 主色 outline，偏移 2px），满足键盘可操作。

### 5.8 文案与可理解性

- 标题、按钮、空状态文案使用简体中文，语气专业友好，避免营销化表述。
- 危险操作二次确认文案明确后果，如"关闭职位后候选人将无法继续投递，已在流程中的候选人不受影响"。
- 时间展示统一格式: `YYYY-MM-DD HH:mm`；"刚刚/N 分钟前"用于列表与时间线的最近活动。

## 6. Backend/Data

本需求不涉及真实后端实现。为便于下游编码节点，记录前端对数据的期望契约（仅展示字段，不构成正式 API 定义）:

- Job: `{ id, title, departmentId, departmentName, location, headcount, salaryMin?, salaryMax?, experience(Enum: 应届/1-3年/3-5年/5-10年/10年以上), education(Enum: 不限/大专/本科/硕士/博士), type(校招/社招/实习), ownerId, ownerName, status(draft/open/paused/closed), jd(rich text), channels[], createdAt, updatedAt }`
- Candidate: `{ id, name, avatar?, phone, email, gender?, age?, education, school?, major?, yearsOfExperience, currentCompany?, currentTitle?, tags[], source, appliedJobId, currentStage, stageEnteredAt, createdAt, updatedAt, experiences[], educations[], timeline[] }`
- Stage 枚举顺序: `screening → shortlist → interview1 → interview2 → hr_chat → offer → onboarded | rejected`

字段具体枚举值、是否必填、长度限制等 `待确认`，由下游技术设计节点确定。

## 7. NFR / DFX

- 兼容性: 原型兼容 Chrome/Edge/Safari 最近两个大版本桌面端；不要求兼容 IE。
- 性能: 首屏原型资源总包体 ≤ 1.5MB（无大型图片依赖）；列表/看板首次渲染 < 500ms（基于 mock 数据）。
- 可访问性: 所有图片/图标具备 alt/aria-label；键盘 Tab 序遵循视觉顺序；颜色对比度满足 WCAG AA（正文 ≥ 4.5:1）。
- 可维护性: 原型代码以 HTML + CSS + 原生 JS 组织，按页面分块，CSS 变量集中定义主题色，便于后续替换为前端框架组件。
- 安全: 原型不处理真实凭据；登录表单不使用 `autocomplete="off"` 完全禁止密码管理器，但在真实实现中需遵循企业安全规范（`待确认`）。
- 发布/回滚: 本节点产物为静态 HTML 原型，通过 agentnative artifacts 登记；后续编码节点以原型为基线进行真实开发，不存在数据迁移风险。
